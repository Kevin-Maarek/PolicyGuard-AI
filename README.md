# PolicyGuard AI

**קיים סרטון המחשה בREPO(example_video_demo.mp4) כדי שלא תצטרכו להריץ את הדמו מקומית, אבל במידה וכן תרצו קיים גם מסמך "בנקאי" שתוכלו להיעזר בו או שתוכלו ליצור מסמך דוגמא משלכם ולנסות בעצמכם.**

היי חגי/צוף

אחרי הפגישה שלנו הסתקרנתי לגבי תוכנת הSAS והתחלתי לבדוק אילו יכולות יש בה ואיפה אפשר לשלב AI. 
המוצר שהתמקדתי בו הוא **[SAS Intelligent Decisioning](https://support.sas.com/en/software/intelligent-decisioning-support.html)** על פלטפורמת **SAS Viya**.

אחרי שיחה עם שני חברים שעובדים בדיסקונט, בנקאי וקצין ציוד, הבנתי שמדי פעם מגיעים עדכונים להנחיות בנושאים כמו פתיחת חשבון והעברות כספים. משם הגיע הרעיון: לבנות דמו שמאפשר להעלות מסמך הנחיות, להבין מה השתנה ולבדוק איך השינוי משתלב בחוקים הקיימים.

לצורך הדמו התמקדתי בחוקים פשוטים של תנאים והשוואות. בניתי סימולטור עם Backend נפרד שמדמה את קריאות ה־API הרלוונטיות של SAS Viya ואת מבני הנתונים שלהן. הדמו רץ מול הסימולטור המקומי שבניתי, והחוקים והנתונים בו נועדו להמחשה.

**מה אפשר לעשות בדמו**

מעלים מסמך PDF או Word, והמערכת מחלצת ממנו את ההנחיות, התנאים והחריגים, יחד עם ציטוט מהמקור. אפשר לשאול שאלות ולתקן את הפרשנות בשפה חופשית לפני שממשיכים.

לאחר אישור הפרשנות, המערכת מחפשת חוקים רלוונטיים ומציגה אותם למשתמש. אפשר לבקש לעדכן חוק קיים, ליצור חוק חדש או להשאיר את המצב כמו שהוא. המשתמש מאשר את ההצעה לבדיקה, ואז המערכת משווה את התנאים ומריצה תרחישים מול המצב הקיים ומול השינוי המוצע בסביבה מבודדת.

בסוף מתקבל הסבר על ההבדלים ועל התוצאות שנצפו. אפשר לאשר רק את הדוח, לשמור טיוטת חוקים נפרדת, או לאשר במפורש את החלת השינוי בסימולטור. עצם השיחה או הרצת הבדיקות לא משנות את החוקים הפעילים.

לדוגמה, אם מסמך חדש מוריד את סף האישור להעברה למוטב חדש מ־30,000 ל־20,000 ש״ח, אפשר לבדוק מה יקרה להעברה של 25,000 ש״ח, האם החריג של העברה מאומתת לאותו בעל חשבון נשמר, והאם חוק אחר עדיין מחייב אישור.

**החוקים בדמו**

כרגע קיימים חמישה חוקים שקשורים להעברות כספים. כל אחד מהם מחייב אישור בנקאי כשהתנאים שלו מתקיימים:

| חוק | התנאים |
|---|---|
| העברה בסכום גבוה למוטב חדש | סכום מעל 100,000 ש״ח ומוטב חדש. |
| העברה מחשבון חדש | חשבון שקיים פחות משבעה ימים וסכום מעל 15,000 ש״ח. |
| אימות מוטב חדש | סכום מעל 30,000 ש״ח ומוטב חדש, למעט העברה מאומתת לאותו בעל חשבון. |
| מכשיר לא מוכר | מכשיר שאינו מהימן וסכום מעל 10,000 ש״ח. |
| ניסיונות התחברות שנכשלו | לפחות חמישה ניסיונות כושלים ב־24 שעות וסכום מעל 5,000 ש״ח. |

בסימולטור אפשר להזין את ששת הערכים הבאים ולראות את ההחלטה ואת החוקים שהופעלו:

| ערך | משמעות |
|---|---|
| `amount` | סכום ההעברה בשקלים. |
| `new_beneficiary` | האם זה מוטב חדש — 0 או 1. |
| `same_owner_verified` | האם זו העברה מאומתת לאותו בעל חשבון — 0 או 1. |
| `trusted_device` | האם המכשיר מהימן — 0 או 1. |
| `account_age_days` | גיל החשבון בימים. |
| `failed_logins_24h` | מספר ניסיונות ההתחברות שנכשלו ב־24 השעות האחרונות. |

התוצאה היא ״המשך״ או ״נדרש אישור בנקאי״. 

**קריאות ה־API של SAS שמופיעות בדמו**

הנתיבים הבאים הם אלה שמתועדים ב־SAS Viya ומשמשים את המערכת מול הדמו.

| קריאה | למה היא משמשת אצלנו |
|---|---|
| `GET /decisions/flows` | שליפת רשימת ההחלטות לצורך סנכרון ואינדוקס. |
| `GET /decisions/flows/{decisionId}` | קריאת מבנה ההחלטה וקבוצות החוקים שמשתתפות בה. |
| `GET /businessRules/ruleSets` | שליפת קבוצות החוקים בסנכרון ובאיתור טיוטה שנשמרה. |
| `GET /businessRules/ruleSets/{ruleSetId}` | קריאת קבוצת חוקים, כולל החוקים עצמם בפורמט Integral. |
| `GET /businessRules/ruleSets/{ruleSetId}/rules` | קריאת החוקים בטיוטה כדי לבדוק מה כבר נשמר. |
| `POST /businessRules/ruleSets` | יצירת קבוצת חוקים נפרדת לשמירת טיוטה שאושרה. |
| `POST /businessRules/ruleSets/{ruleSetId}/rules` | הוספת החוקים לקבוצת הטיוטה. |
| `POST /microanalyticScore/modules/{moduleId}/steps/execute` | העברת פרמטרים למודול ההחלטה וקבלת התוצאה. |

**אינדוקס החוקים, חיפוש היברידי ו־RAG**

כדי למצוא את החוקים שקשורים למסמך, המערכת בונה מראש מאגר חיפוש מתוך ההחלטות וקבוצות החוקים שנשלפות דרך ה־API. לכל חוק נבנה טקסט לחיפוש שכולל את השם שלו, תיאור כשיש כזה, התנאים והפעולה שהוא מחזיר. לצד הטקסט נשמרים גם הנתונים המקוריים, הגרסה והקשרים בין החוק, קבוצת החוקים וההחלטה.

הטקסט עובר דרך מודל embeddings, שמייצר לו ייצוג מספרי של המשמעות, והווקטור נשמר ב־PostgreSQL עם pgvector. במקביל, מתוך הטקסטים נבנה בזיכרון אינדקס לחיפוש מילולי ב־BM25, שמתעדכן כשהתוכן במאגר משתנה. הסנכרון מול הסימולטור מתחיל בעליית המערכת ורץ שוב כל חמש דקות כברירת מחדל. אם הטקסט ומודל ה־embeddings לא השתנו, המערכת משתמשת בווקטור הקיים וחוסכת חישוב חוזר.

כשמגיעים לשלב חיפוש החוקים, נבנית שאילתה לכל דרישה שחולצה מהמסמך, מתוך הציטוט שלה ומונחים קשורים. אותה שאילתה משמשת לשני סוגי חיפוש:

- **BM25 — חיפוש מילולי:** מדרג חוקים לפי התאמה של מילים ומונחים, למשל שמות שדות או מונחים שמופיעים גם בדרישה וגם בחוק.
- **חיפוש סמנטי:** מייצר embedding לשאילתה ומשווה אותו לווקטורים של החוקים כך אפשר למצוא גם חוקים שעוסקים באותו נושא בניסוח שונה.

שני הדירוגים מתאחדים באמצעות **Reciprocal Rank Fusion (RRF)** לרשימת מועמדים אחת. 

**מה יש מאחורי הקלעים**

רציתי להדגים לכם חיבור של כמה יכולות לתהליך אחד:

- **API של SAS**
- **LangGraph**
- **RAG וחיפוש היברידי**
- **בדיקות לוגיות ותרחישים**

המערכת בנויה ב־Python ו־FastAPI בצד השרת, React ו־TypeScript בצד הממשק, ו־PostgreSQL עם pgvector לאחסון ולחיפוש. מודלי השפה וה־embeddings רצים כברירת מחדל מקומית דרך Ollama, והאפליקציה עולה עם Docker Compose.
